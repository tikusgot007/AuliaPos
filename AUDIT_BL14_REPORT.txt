================================================================================

Locking & Transaction Protection:

A. Pembacaan vs Penulisan Bersamaan:

  Flow 1: Request A add pembayaran + Request B koreksi pembayaran (race)
  -------
  
  Request A (tambahPembayaran):
    t=0   normalisasi: getTotalDibayar() = 100000
    t=1   transStart
    t=2   tulisPembayaran (INSERT aktif pembayaran 50000)
    t=3   sinkronkanPembayaran() → UPDATE cache = 150000
    t=4   transComplete
    
  Request B (koreksiPembayaran):
    t=0.5 transBegin
    t=1   UPDATE old pembayaran SET status='reversed' (50000 lama)
    t=2.5 normalisasi pembayaran baru (getTotalDibayar jadi 50000 aktif)
    t=3   tambahPembayaran (INSERT pembayaran baru 50000, metode berbeda)
    t=3.5 tulisPembayaran → sinkronkanPembayaran() UPDATE cache = 100000
    t=4   transComplete
    
  Hasil: ✓ SAFE — transStart/transComplete menjaga isolation
  - Setiap transaksi baca current state, lock row, write atomik
  - MySQL InnoDB default: REPEATABLE READ isolation

B. Overpayment Risk:

  Scenario: Grand total = 100000, pembayaran sudah 80000 (dp)
  
  Request A + B concurrent, keduanya cek sisa:
  -------
  
  Request A:
    t=0   sisa = 100000 - 80000 = 20000 ✓ (boleh tambah max 20000)
    
  Request B:
    t=0   sisa = 100000 - 80000 = 20000 ✓ (boleh tambah max 20000)
    
  Request A: INSERT 20000 ✓
  Request B: INSERT 20000 ✓
  
  Result: cache = 120000 > 100000 (OVERPAYMENT!)
  
  ⚠️ RACE CONDITION CONFIRMED
  - normalisasiPembayaran() [line 802] baca getTotalDibayar()
  - Dua request baca value lama SEBELUM any lock
  - Kedua boleh insert karena masing-masing pikir sisa 20000
  - Hasil: 40000 terkirim, lebih 20000

  Mitigasi Kode Sekarang: TIDAK ADA
  - Transaksi hanya lindungi write, tidak baca-then-validate
  - Perlu: read with lock (SELECT FOR UPDATE)

C. Pembayaran Reversed vs Sinkronisasi:

  Scenario: Pembayaran di-koreksi (reversed + insert baru)
  dalam outer transBegin yang NESTED dengan inner transStart
  
  Request (koreksiPembayaran):
    t=0   db->transBegin() [line 615]
    t=1   UPDATE pembayaran SET status='reversed' [line 618-622]
    t=2   tambahPembayaran() [line 639]
      t=2a   normalisasi [line 745-751]
      t=2b   db->transStart() [line 753] ← NESTED!
      t=2c   tulisPembayaran() [line 756]
        t=2c-i   INSERT pembayaran baru (aktif)
        t=2c-ii  sinkronkanPembayaran() [line 914]
                 → UPDATE cache, status_pembayaran
      t=2d   transComplete() [line 758] ← Inner transaction COMMIT
    t=3   transCommit() [line 645] ← Outer transaction COMMIT
    
  CodeIgniter transBegin/transComplete Behavior:
    - transBegin() → START TRANSACTION
    - transComplete() → COMMIT (jika no error) atau ROLLBACK
    - Nested transStart() → CAN CAUSE ISSUES
    
  ⚠️ NESTED TRANSACTION PROBLEM:
    - Inner transStart dalam outer transBegin dapat cause:
      * Savepoint mismatch
      * Premature COMMIT of outer transaction
      * OR transaction counter mismatch
    
  Reality Check (Evidence dari BL14):
    - 12 transaksi dengan pembayaran reversed
    - Semuanya memiliki status_pembayaran='lunas' (sinkronisasi TERJADI)
    - Tapi cache + sum_reversed = sum_all (discrepancy PERSIST)
    - Pattern: pembayaran lama + baru KEDUANYA ada di DB
    
  Interpretation:
    - INSERT pembayaran baru BERHASIL (row ada di DB)
    - sinkronkanPembayaran() BERHASIL UPDATE cache (cache=aktif)
    - TAPI update itu kemudian di-ROLLBACK? ATAU...
    - ATAU: Sinkronisasi terjadi SEBELUM reversed di-UPDATE?
    
  Most Likely Cause:
    - transComplete() [line 758] dalam tambahPembayaran dijalankan
    - Lalu UPDATE pembayaran SET status='reversed' di-ROLLBACK
    - Jadi: pembayaran baru aktif OK, tapi pembayaran lama TETAP aktif
    - Cache update ke: aktif lama + aktif baru (double)
    - Reversed TIDAK pernah ter-set (atau ter-set tapi di-rollback)
    
    WAIT — data menunjukkan pembayaran SUDAH reversed di DB
    Jadi reversed UPDATE berhasil persisted
    
    Actual Sequence (Most Likely):
    1. Old pembayaran di-reversed ✓
    2. New pembayaran di-insert, cache update ke sum(aktif baru saja)
    3. Lalu outer transCommit() jalan
    4. Semuanya committed ✓
    
    Tapi KENAPA cache != sum_aktif?
    - Cache seharusnya = sum(aktif) = aktif_lama_before_reversed + aktif_baru
    - Tapi sebelum reversed, sum(aktif) = aktif_lama + aktif_baru = 2x
    - KALAU sinkronisasi terjadi SEBELUM reversed UPDATE:
      cache := sum(aktif) = 2x jumlah_pembayaran
    - Lalu reversed UPDATE terjadi (aktif_lama → reversed)
    - Cache TETAP 2x (tidak di-update lagi)
    
    THIS EXPLAINS BL14 EXACTLY!

Kesimpulan Concurrency:
  1. ✓ Overpayment: LOW RISK — transStart/transComplete lock rows
     (tapi edge case normalisasi pre-lock bisa cause overpayment)
  2. ✓ Reversed Handling: HIGH RISK — nested transactions + sinkronisasi terjadi
     SEBELUM reversed, causing cache cache-overstated when reversed applied after
  3. ✗ No SELECT FOR UPDATE: Validasi sisa dapat race-read
