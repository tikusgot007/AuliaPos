| Nama Subbab        | Archive Transaksi                                                                                                                                                                                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tujuan             | Memindahkan transaksi historis dari database operasional MySQL ke database archive SQLite agar database utama tetap ringan tanpa kehilangan histori transaksi.                                                                                                                                        |
| Deskripsi          | Archive dijalankan manual oleh Admin melalui `/archive-transaksi`. `TransaksiArchiveService` memindahkan transaksi satu bulan penuh beserta detail dan pembayaran ke SQLite terpisah. Data archive bersifat read-only dan digunakan kembali oleh pencarian, laporan, serta detail transaksi historis. |
| Aturan Bisnis      | Bulan eligible jika berjarak minimal 6 bulan penuh dari bulan berjalan. Status transaksi tidak diubah saat archive, termasuk `mangkrak`. ID archive mempertahankan ID MySQL. Nama pelanggan dan kasir di-snapshot agar archive tetap self-contained.                                                  |
| Alur               | Pilih bulan → preview read-only → validasi eligibility → tulis backup JSON → salin transaksi/detail/pembayaran ke SQLite secara idempotent → validasi jumlah row dan total `grand_total` → jika valid, hapus data MySQL dalam transaction → histori selanjutnya dibaca dari archive.                  |
| Hak Akses          | Admin-only. Proteksi dilakukan dua lapis: `AuthFilter` dan pengecekan role inline di `ArchiveTransaksi`.                                                                                                                                                                                              |
| Kondisi & Batasan  | Tidak otomatis/cron. Jika validasi archive gagal, data MySQL tidak dihapus. `Tagihan::detail()` belum melakukan fallback ke archive. Reprint transaksi archive sengaja tidak didukung.                                                                                                                |
| Data yang Terlibat | MySQL `transaksi`, `detail_transaksi`, `pembayaran`; SQLite `transaksi_archive`, `detail_transaksi_archive`, `pembayaran_archive`; backup JSON; `archived_at`, `archived_period`.                                                                                                                     |
| Catatan            | Archive menggunakan koneksi SQLite terpisah di `WRITEPATH/archive/aulia_pos_archive.db`. Schema dapat self-initialize/self-heal ketika `TransaksiArchiveService` digunakan. Laporan dan pencarian menggunakan pendekatan dual-source MySQL + archive.                                                 |
| Status             | Aktif di v2.1                                                                                                                                                                                                                                                                                         |

| Nama Subbab        | Session Management                                                                                                                                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tujuan             | Menyimpan identitas login dan konteks user selama penggunaan aplikasi serta memberikan session timeout dan role gating.                                                                                                                                                                                       |
| Deskripsi          | AULIA menggunakan session-based authentication melalui `AuthFilter`, tanpa library authentication khusus. Saat login berhasil, session menyimpan `id_user`, `username`, `inisial`, `role`, `isLoggedIn`, dan `last_activity`.                                                                                 |
| Aturan Bisnis      | Session dianggap valid jika `isLoggedIn` aktif dan aktivitas terakhir tidak lebih dari 30 menit. Setiap request yang melewati `AuthFilter` memperbarui `last_activity`. Jika timeout, session dihancurkan dan user diarahkan ke login.                                                                        |
| Alur               | Login berhasil → session dibuat → request ke route ber-filter `auth` → cek `isLoggedIn` → cek timeout → update `last_activity` → lanjut ke controller. Logout menghancurkan session dan kembali ke `/login`.                                                                                                  |
| Hak Akses          | Role dasar hanya `admin` dan `kasir`. `AuthFilter::$adminRoutes` memberikan gate tambahan untuk route seperti laporan, jadwal, migrasi manual, archive transaksi, produk, kategori, dan closing kas.                                                                                                          |
| Kondisi & Batasan  | Filter `auth` diterapkan per-route, bukan global. Karena itu route yang tidak diberi filter `auth` tidak otomatis memperoleh perlindungan session. Role gate juga berbasis prefix URI yang didefinisikan di `AuthFilter`.                                                                                     |
| Data yang Terlibat | Session `isLoggedIn`, `id_user`, `username`, `inisial`, `role`, `last_activity`; `AuthFilter`; `Auth` controller; route filter `auth`.                                                                                                                                                                        |
| Catatan            | Session timeout adalah **idle timeout**, bukan batas maksimum sejak login. Request yang berhasil melewati filter memperbarui waktu aktivitas. `is_active` user bukan pemeriksaan login di `prosesLogin()` pada implementasi v2.1, sehingga status aktif user dan validitas session merupakan dua hal berbeda. |
| Status             | Aktif di v2.1                                                                                                                                                                                                                                                                                                 |
